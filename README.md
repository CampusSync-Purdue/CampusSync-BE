# CampusSync Backend

Backend API for CampusSync, built with Node.js, Express, and TypeScript.

## Prerequisites

- Node.js 18 or later
- npm

Verify your local installation:

```bash
node --version
npm --version
```

## Install dependencies

From the `CampusSync-BE` directory, run:

```bash
npm install
```

The direct dependency versions in `package.json` are pinned so team members install the same Express, CORS, dotenv, TypeScript, and related type-package versions.

## Environment variables

Create a local `.env` file from the template:

```bash
cp .env.example .env
```

Local development uses port `5050` because port `5000` may be used by AirTunes on macOS.

```env
PORT=5050
```

Never commit `.env`; it may later contain database credentials and other secrets. Commit changes to `.env.example` when a new variable is required.

## Local PostgreSQL database

This project runs PostgreSQL 16 in Docker.

### Start the database

1. Create `.env` from the template and set the `POSTGRES_*` values.

```bash
cp .env.example .env
```

2. Build the database image once, then start it:

```bash
./dev-env postgres      # Build the PostgreSQL image
./dev-env postgres up   # Start PostgreSQL, apply migrations, list its tables
```

`./dev-env postgres up` does not build an image. It starts the existing local
container, waits until PostgreSQL is healthy, and runs `npm run db:migrate`
(run `npm install` first). If `.env` is missing, the command stops without
creating or changing files.

### Schema and migrations (Drizzle ORM)

All queries go through [Drizzle ORM](https://orm.drizzle.team) on the existing
`pg` connection pool (`src/db/index.ts` exports `db`).

- `src/db/schema.ts` is the source of truth for the `users`, `rooms`, and
  `reservations` tables.
- `drizzle/` holds the SQL migrations generated by drizzle-kit. Commit them.
- `drizzle/0001_reservation_overlap.sql` is hand-written: Drizzle cannot
  express the `btree_gist` extension or the `EXCLUDE` constraint that stops two
  active reservations for the same room from overlapping.

| Command | Purpose |
| ------- | ------- |
| `npm run db:generate` | Create a migration after editing `src/db/schema.ts` |
| `npx drizzle-kit generate --custom --name <name>` | Create an empty migration for SQL Drizzle cannot express |
| `npm run db:migrate` | Apply pending migrations to `DATABASE_URL` |
| `npm run db:studio` | Browse the database in Drizzle Studio |

Docker no longer creates tables on first start. A database volume created
before the move to migrations already has tables that the first migration
would try to create again, so reset it once:

```bash
docker compose down -v
./dev-env postgres up
```

This permanently deletes local database data.

### Connect to PostgreSQL

From your machine:

```bash
docker compose exec postgres psql -U campussync_app -d campussync
```

Use this connection string from the backend when it runs on your machine:

```text
postgresql://campussync_app:your-password@localhost:5432/campussync
```

Containers on `campussync_network` use the Docker service hostname:

```text
postgresql://campussync_app:your-password@postgres:5432/campussync
```

## Bootstrap the first administrator

CampusSync provides a repeatable environment-driven script for creating the
first administrator account.

Before running the bootstrap, make sure PostgreSQL is running and configure
these variables in your local `.env` file:

```env
ADMIN_NAME=replace-with-admin-name
ADMIN_EMAIL=replace-with-admin-email
ADMIN_PASSWORD=replace-with-a-strong-admin-password
```

Do not commit `.env` or put real credentials in `.env.example`.

To create the first administrator, run:

```bash
npm run bootstrap-admin
```

The script checks whether an administrator already exists. If one does not
exist, it creates the administrator using the supplied environment variables
and stores a bcrypt password hash. If an administrator already exists, the
script leaves the existing account unchanged.

For local PostgreSQL, start the database (which also applies migrations) before
running the bootstrap:

```bash
./dev-env postgres up
npm run bootstrap-admin
```

The bootstrap command is safe to run again after an administrator has already
been created.

## Run the API

Start the development server:

```bash
npm run dev
```

Other commands:

```bash
npm run build
npm start
```

`npm run build` compiles TypeScript from `src/` into `dist/`. `npm start` runs the compiled application.

## Request logs

Each API request is appended to `logs/application.log` as a JSON line. The logger records only the timestamp, HTTP method, route path, status code, and duration. Unhandled errors are also logged with error details and a stack trace, while the client receives a safe generic error message. Passwords, authorization headers, JWTs, and request bodies are deliberately excluded. The `logs/` directory is ignored by Git.


## Registration endpoint

Create an account:

```bash
curl -i -X POST http://127.0.0.1:5050/api/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"name":"Varun Teja","email":"varun@campussync.edu","password":"Password1"}'
```

Successful responses are `201` and contain the new user without any password data:

```json
{
  "message": "Your account has been created.",
  "user": {
    "id": "54446290-115c-4f4d-8c6e-810640df7638",
    "name": "Varun Teja",
    "email": "varun@campussync.edu",
    "role": "user",
    "createdAt": "2026-10-01T22:52:11.291Z"
  }
}
```

Failure responses carry a `message` plus per-field `errors`:

| Status | Meaning |
| ------ | ------- |
| `400`  | A field is missing or invalid |
| `409`  | The email address is already registered |
| `500`  | Unexpected server error (details are logged, not returned) |

Rules enforced by the endpoint:

- Name is 2 to 100 characters.
- Email must be well formed, at most 254 characters, and is stored lowercased.
  Uniqueness is case-insensitive.
- Password is 8 to 128 characters and must contain a lowercase letter, an
  uppercase letter, and a number.
- Passwords are hashed with bcrypt (cost 12). The hash never leaves the backend.
- Every new account is assigned the default `user` role; a `role` supplied by
  the client is ignored.

Users are stored in the Postgres `users` table by
`src/repositories/userRepository.ts`. Registration, login, and `GET /api/auth/me`
all read that table, so a newly registered account can sign in, and the JWT
`id` is the user's database UUID.

## Rooms and reservations

Seed the demo rooms (fixed ids, open 08:00–20:00 every day; safe to re-run):

```bash
npm run seed-rooms
```

Booking rules use the campus time zone (`CAMPUS_TIMEZONE`, default
`America/Indiana/Indianapolis`).

| Endpoint | Auth | Purpose |
| -------- | ---- | ------- |
| `GET /api/rooms` | No | Active rooms with opening hours |
| `GET /api/rooms/:roomId/availability?date=YYYY-MM-DD` | Yes | Opening hours and booked ranges for a campus date. Each range has `isMine`; no other user details are returned |
| `POST /api/reservations` | Yes | Create an active reservation for the signed-in user |

`POST /api/reservations` takes `{ roomId, startTime, endTime }` as ISO 8601
timestamps with an offset (e.g. `2026-10-27T10:00:00-04:00`). The user comes
from the token; a `userId` or `status` in the body is ignored. Rules:

- 30 minutes to 4 hours, on the hour or half hour, within one campus day
- In the future and at most 30 days ahead
- Within the room's opening hours
- No overlap with another active reservation (enforced by the database)

| Status | Meaning |
| ------ | ------- |
| `201` | Created; returns `{ message, reservation }` |
| `400` | Invalid fields or outside opening hours (`errors` per field) |
| `401` | Not signed in, or the account no longer exists |
| `404` | Room does not exist or is inactive |
| `409` | Overlaps another reservation |

## Tests

Integration tests use a separate database that they truncate between tests.
Create it once and point `TEST_DATABASE_URL` at it:

```bash
./dev-env postgres test-db
# then in .env:
# TEST_DATABASE_URL=postgresql://campussync_app:<password>@localhost:5432/campussync_test
npm test
```

`npm test` preloads `scripts/test-env.ts`, which swaps `DATABASE_URL` for
`TEST_DATABASE_URL` and refuses to run if it is unset or the same as
`DATABASE_URL`. The test helpers also refuse to reset a database whose name
does not end in `_test`. Migrations are applied automatically, and test files
run one at a time because they share the database.

Tests run on the Node.js built-in test runner through `tsx`, and live beside the
code they cover as `*.test.ts`. They are excluded from `npm run build`.

## Project structure

```text
src/
  config/         # Environment and application configuration
  constants/      # Shared constant values, including HTTP status codes
  controllers/    # Request handlers
  db/             # Drizzle schema, client, migrations runner, pg error helpers
  middleware/     # Express middleware
  repositories/   # Data access and persistence
  routes/         # API route definitions
  services/       # Business logic and external integrations
  test/           # Test-only helpers (test database, test server)
  types/          # Shared TypeScript types
  validation/     # Request payload validation
  app.ts          # Express app and middleware configuration
  server.ts       # Environment loading and HTTP server startup
```
